# V1.8～V1.9 PRD：学习日志与 Blog 发布

> 产品：考研学习进度网站  
> 文档版本：V1.8～V1.9  
> 目标读者：产品设计者、人类开发者、Codex / 其他代码代理  
> 当前基线：V1.5 Beta 信息架构已确定，一级页面仍为「学习进度 / 今日 / 数据分析 / 设置」  
> 本文重点：V1.8「学习日志」、V1.9「Blog 发布」

---

# 0. 文档目的

当前网站已经能够记录：

- 某一小节计划什么时候学习；
- 某一小节实际什么时候学完；
- 某一小节是否已经复习；
- 今天有哪些任务；
- 哪些任务已经逾期。

但这些数据只能回答：

> “我学到了哪里？”

无法回答：

> “我当时是怎么理解的？”  
> “今天学习过程中发生了什么？”  
> “为什么这一节让我印象很深？”  
> “某一天我的状态、想法和学习内容是什么？”

因此，需要新增一套「学习日志」能力。

本次迭代的目标不是做一个独立笔记软件，也不是做一个完整 CMS，而是给现有学习进度系统增加一条连续的、按时间组织的文字记录流。

日志与学习进度之间应该是：

```text
学习进度
记录客观状态：计划 / 学完 / 复习

日志
记录主观内容：想法 / 理解 / 过程 / 当日记录
```

二者使用同一个学习项目与小节体系，但互不替代。

# 1. 总体产品原则

## 1.1 日志不是第五个一级页面

一级导航继续保持：

```text
学习进度
今日
数据分析
设置
```

日志放在「今日」页面的下一个完整页面区域。

用户进入「今日」后：

```text
第一屏：今日
↓ 向下滚动
第二屏：日志
```

即：

```text
┌──────────────────────────────┐
│ 今日                         │
│                              │
│ 今日计划                     │
│ 逾期                         │
│ 未复习                       │
└──────────────────────────────┘
               ↓
┌──────────────────────────────┐
│ 日志                         │
│                              │
│ 8 月 14 日                   │
│ ...                          │
│                              │
│ 8 月 13 日                   │
│ ...                          │
└──────────────────────────────┘
```

实现上建议保持同一个 route / 页面容器，不新增 `journal` 一级路由。

可以使用普通纵向滚动，也可以在桌面端增加轻量的 `scroll-snap`，但不能影响用户正常滚动。

---

## 1.2 日志只有一种数据类型

不建立：

- 今日笔记；
- 小节笔记；
- 日记；
- Blog 草稿；

等多套互相独立的数据。

底层只存在一种：

```text
JournalEntry
```

区别只在于：

- 创建时间不同；
- 是否关联学习对象；
- 是否已经发布到 Blog。

这样从今日、小节或日志区域创建的记录，最终都进入同一条时间流。

---

## 1.3 Blog 是发布出口，不是日志数据库

学习网站中的日志可以是：

- 私人的；
- 零散的；
- 没有标题的；
- 只适合自己看的；
- 尚未整理完成的。

只有用户主动选择某一条日志并执行「发布到 Blog」时，才进入公开发布流程。

因此：

```text
学习日志
   ↓ 用户主动选择
Blog 发布稿
   ↓
GitHub Blog
```

不能设计成：

```text
保存日志
= 自动同步 Blog
```

# 3. V1.8 — Journal

# 3.1 版本目标

V1.8 要解决：

> 用户在学习过程中随时写下一条记录，并让这些记录按照时间像日记一样自然串起来。

同时允许部分记录与具体小节建立联系，例如：

```text
2026/08/14 16:20

今天重新看了一遍 CPU 调度。
之前一直混淆周转时间和带权周转时间……

关联：
操作系统 · 2.3 处理机调度
```

也允许完全不关联学习内容：

```text
2026/08/14 22:10

今天下午状态很差，晚上反而效率不错。
```

# 4. JournalEntry 数据模型

## 4.1 核心结构

推荐：

```json
{
  "id": "20260814002",
  "createdAt": "2026-08-14T16:20:00+08:00",
  "updatedAt": "2026-08-14T16:28:00+08:00",

  "title": null,
  "content": "今天重新看了一遍 **CPU 调度**……",

  "context": {
    "type": "section",
    "projectId": "408",
    "subjectId": "os",
    "sectionId": "os-2-3"
  },

  "publish": {
    "status": "local",
    "publishedAt": null,
    "blogUrl": null,
    "blogPostId": null
  }
}
```

---

## 4.2 context 数据结构

数据层从一开始支持：

```text
none
project
subject
section
```

示例：

### 无关联

```json
"context": null
```

### 项目级

```json
{
  "type": "project",
  "projectId": "408"
}
```

### 科目级

```json
{
  "type": "subject",
  "projectId": "408",
  "subjectId": "os"
}
```

### 小节级

```json
{
  "type": "section",
  "projectId": "408",
  "subjectId": "os",
  "sectionId": "os-2-3"
}
```

---

## 4.3 V1.8 UI 只开放两种关联方式

虽然底层支持四种状态，但 V1.8 的用户界面只允许：

```text
○ 不关联
○ 关联一个小节
```

暂不提供：

```text
关联整个 408
关联整个操作系统
```

原因：

当前最明确、最常用的上下文仍然是具体小节。先保留数据扩展能力，不增加 UI 复杂度。

# 5. Journal ID 规则

## 5.1 格式

日志内部 ID 使用：

```text
YYYYMMDD + 当日三位序号
```

例如：

```text
20260814001
20260814002
20260814003
```

---

## 5.2 编号规则

必须满足：

1. 根据用户本地日期生成；
2. 当天第一条为 `001`；
3. 每新增一条递增；
4. ID 一经生成永久不变；
5. 修改正文不改变 ID；
6. 修改关联对象不改变 ID；
7. 后续若允许修改显示日期，也不改变 ID；
8. 删除 `002` 后不重新占号；
9. 当日下一条继续生成 `004`；
10. UI 默认不需要一直显示该 ID。

---

## 5.3 为什么采用该规则

日志不要求标题，因此系统仍需要一个稳定、可读、可迁移的内部标识。

该 ID 后续还可以用于：

- Blog 默认 slug；
- Markdown 文件名；
- 导出文件定位；
- 数据迁移；
- Debug。

---

# 6. 日志标题

## 6.1 标题非必填

普通日志不要求填写标题。

创建界面默认只要求：

```text
正文
关联对象（可选）
```

原因：

日志首先是随手记录。

如果强制标题，会增加记录成本，例如：

```text
“今天 CPU 调度终于弄懂了……”
```

用户还需要先想一个：

```text
“CPU 调度学习心得”
```

没有必要。

---

## 6.2 title 字段仍然保留

数据结构保留：

```json
"title": null
```

以后：

- 用户可以主动补标题；
- 发布 Blog 时可以填写正式标题。

## 7.2 今日区域

```text

```


```text

```

# 8. 小节中的日志展示

## 8.1 不把日志正文直接塞入目录

学习进度页仍以目录为主。

禁止：

```text
2.3 处理机调度
├ 今天理解了……
├ 8 月 12 日……
├ 8 月 10 日……
```

这样会破坏目录页面的密度。

---

## 8.2 有记录时显示数量

例如：

```text
2.3 处理机调度             3 条记录
```

没有记录时，不需要长期显示：

```text
0 条记录
```

避免增加噪声。

---

## 8.3 点击数量查看相关日志

点击：

```text
3 条记录
```

建议打开右侧抽屉：

```text
2.3 处理机调度

相关记录

08/14 16:20
今天重新看了一遍 CPU 调度……

08/12 21:10
RR 的时间片这里……

08/10 18:30
第一次学习……
```

点击具体记录可进入完整查看 / 编辑状态。

# 9. 日志第二屏

## 9.1 基本结构

```text
日志

[搜索...]            [筛选]

8 月 14 日 · 星期五

16:20
今天重新看了一遍 CPU 调度……
操作系统 · 2.3 处理机调度

11:03
上午状态一般，数学推进比较慢。


8 月 13 日 · 星期四

22:10
……
```

---

## 9.2 排序

默认：

```text
createdAt DESC
```

即：

> 最新记录在最上方。

日期内同样按时间倒序。

---

## 9.3 日期分组

按用户本地日期分组。

不能直接按 UTC Date 分组。

# 10. 日志卡片展示

每条记录在时间流中至少展示：

- 时间；
- 正文摘要；
- 关联对象（如果存在）。

标题如果为空则不展示标题区域。

示例：

```text
16:20

今天重新看了一遍 CPU 调度。
之前一直混淆周转时间和带权周转时间……

操作系统 · 2.3 处理机调度
```

正文过长时截断，点击进入完整记录。

# 11. 日志搜索

## 11.1 V1.8 必须支持正文搜索

搜索对象：

- `content`

```text
无关联
有关联
```

# 13. Markdown 编辑器

# 13.1 设计目标

V1.8 不做 Typora / Notion 式所见即所得编辑器。

原因：

所见即所得会显著增加：

- 光标定位；
- DOM 与 Markdown 双向同步；
- 列表行为；
- 粘贴；
- 撤销；
- 输入法；
- 手机端兼容；

等复杂度。

本版本采用：

> Markdown 源码编辑 + 实时渲染预览。

---

# 14. 编辑模式

桌面端支持三种查看方式：

```text
编辑
分栏
预览
```

---

## 14.1 编辑

只显示 Markdown 输入区。

适合专注写作。

---

## 14.2 分栏

```text
┌────────────────────┬────────────────────┐
│ Markdown           │ 实时预览            │
│                    │                    │
│ ## CPU 调度        │ CPU 调度            │
│                    │                    │
│ - FCFS             │ • FCFS             │
│ - RR               │ • RR               │
└────────────────────┴────────────────────┘
```

输入时右侧实时更新。

---

## 14.3 预览

只显示 Markdown 渲染后的内容。

适合检查最终效果。


# 17. 数学公式

## 17.1 V1.8 必须支持

数学公式属于正式需求。

支持：

### 行内公式

```markdown
时间复杂度为 $O(n^2)$。
```

### 块级公式

```markdown
$$
\int_0^1 f(x)\,dx
$$
```

---

## 17.2 渲染

可以使用成熟方案，例如：

- KaTeX；
- MathJax；

优先选择加载快、适合静态渲染的实现。

---

## 17.3 Markdown 源码仍然是唯一正文

公式不得另外保存为结构化对象。

仍然保存：

```text
$content
```

例如：

```markdown
由 Cauchy-Schwarz 不等式，

$$
\left(\int_a^b f(x)g(x)\,dx\right)^2
\le
\int_a^b f^2(x)\,dx
\int_a^b g^2(x)\,dx
$$
```

这样以后迁移到 Blog 时保持兼容。

---

# 18. 图片

V1.8 不做本地图片上传。

允许正文中手写：

```markdown
![图片](https://example.com/image.png)
```

如果 Markdown renderer 支持，即可正常显示远程图片。

暂不解决：

- 手机拍照上传；
- 拖拽上传；
- 剪贴板图片上传；
- GitHub 图床；
- 对象存储。

图片上传与 Blog 发布的图片策略后续统一设计。

# 20. 自动保存

V1.8 建议实现草稿自动保存。

最低要求：

- 编辑已有日志时，未点击保存前不立即覆盖正式正文；
- 如果页面意外刷新，尽量恢复未提交文本。

可使用临时 draft：

```text
journalDraft
```

草稿不属于正式 JournalEntry。

如果工程复杂度较高，至少应在关闭编辑器且有未保存内容时提示：

```text
内容尚未保存，确定离开？
```

# 21. 编辑日志

允许修改：

- title；
- content；
- context。

每次正式保存后更新：

```text
updatedAt
```

不得修改：

```text
id
createdAt
```

# 22. 删除日志

删除属于不可逆内容操作，因此必须确认。

例如：

```text
删除这条日志？

删除后将从日志时间流和相关小节记录中同时消失。

[取消] [删除]
```

删除后：

- 不再显示；
- 小节记录数量重新计算；
- Blog 已发布状态的处理见 V1.9。

V1.8 可先直接删除，不要求回收站。

---

# 23. 小节被删除时的日志处理

如果某个小节以后从目录中被删除：

> 关联日志不得跟着删除。

日志保留原正文和时间。

context 可以标记为失效关联，例如运行时检测：

```text
原关联内容已不存在
```

不要直接把 context 清空，否则历史信息丢失。

```text

```

日志第二屏顶部也可以提供：

```text

```

但不要求复杂动画。

# 25. 日志与项目切换

顶部项目切换器继续生效。

例如当前项目为：

```text
408
```

- 408 关联日志；
- 无关联日志。


# 26. 日志与 Settings

Settings 的：

- 导出全部数据；

# 30. V1.9 — Blog Publishing

# 30.1 版本目标

V1.9 解决：

> 用户写下一条值得公开的学习日志后，可以不依赖电脑本地发帖流程，直接从学习网站发布到个人 GitHub Blog。

Blog 地址：

```text
https://craig9re5.github.io/
```

V1.9 的重点是减少发布摩擦，而不是把学习网站改造成完整 Blog 后台。

---

# 31. 发布入口

日志详情页中增加：

```text
发布到 Blog
```

只有用户主动点击时才进入发布流程。

保存日志本身不得自动触发发布。

---

# 32. 发布前二次编辑

点击发布后进入独立发布表单。

示例：

```text
发布到 Blog

标题
[ CPU 调度重新学习记录 ]

Slug
[ 20260814002 ]

正文
[ Markdown 编辑器 ]

[取消]                  [发布]
```

---

## 32.1 发布稿与原日志分离

发布前允许修改：

- 标题；
- 正文；
- slug；
- Blog 所需元信息。

这些修改默认只作用于发布稿。

不得自动改写原日志。

---

## 32.2 为什么必须分离

原日志可能是：

```text
今天 CPU 调度终于整明白了，
之前真是绕……
```

公开文章可能需要改成：

```text
处理机调度中周转时间、带权周转时间与响应比的理解
```

私人记录与公开文章用途不同，不应强迫共用完全相同的文本。

# 39. 发布技术架构

## 39.1 禁止前端直接保存 GitHub Token

不能：

```text
浏览器 JS
↓
硬编码 GitHub Personal Access Token
↓

```

任何可读取前端资源的人都可能获得凭据。

```text

       ↓

       ↓
受保护的发布 API
       ↓
GitHub API
       ↓
Blog Repository
       ↓
GitHub Pages
```

发布 API 可以使用：

- Cloudflare Worker；

# 48. 最终产品结构

完成 V1.9 后：

```text
学习进度
负责：规划与学习状态

今日
负责：当天执行
  ↓
日志
负责：连续的学习记录

数据分析
负责：历史数据分析

设置
负责：项目、数据与 Blog 连接
```

日志承担了学习进度系统中原本缺失的一部分：

> 进度记录“发生了什么”，日志记录“当时我在想什么”。

而 Blog 只负责：

> 把少量值得公开的日志，进一步整理并发布出去。

两者保持关联，但不互相绑死。
